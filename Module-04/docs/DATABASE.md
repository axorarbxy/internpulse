# Module 4 — Database Design

Module 4 owns only the collections below. It does **not** duplicate Module 1's
users/internships tables — it references them by ID (`recipientId`,
`studentId`, `companyId`, `internshipId`, etc.) and, where needed for
long-term integrity (certificates), stores a **point-in-time snapshot** of the
authoritative data rather than an ongoing copy.

```
User (Module 1, external)
 │
 ├── Notification          (recipientId → User)
 ├── Conversation           (participantIds[] → User)
 │      └── Message         (conversationId → Conversation, senderId → User)
 └── Certificate            (studentId, companyId → User)

Internship (Module 1, external)
 │
 ├── Reminder               (internshipId → Internship, studentId → User)
 ├── DocumentVerification   (internshipId → Internship)
 └── Certificate            (internshipId → Internship)

AuditLog (actorId → User, entityId → any of the above)
```

## Collections

### notifications
`id, recipientId, type, title, message, relatedEntityType, relatedEntityId, isRead, createdAt`
Index: `{ recipientId, isRead, createdAt }`

### conversations
`id, participantIds[], internshipId?, lastMessageAt, createdAt, updatedAt`
Index: `{ participantIds }`

### messages
`id, conversationId, senderId, ciphertext, iv, readBy[], createdAt`
Index: `{ conversationId, createdAt }`
**Never contains plaintext.**

### reminders
`id, internshipId, studentId, reminderType, scheduledFor, sentAt, status, createdAt`
Unique index: `{ internshipId, studentId, scheduledFor }` — this is how
duplicate weekly reminders are prevented.

### document_verifications
`id, documentId, internshipId, verificationStatus, verificationScore, reason, verifiedAt, verifiedBy, source, createdAt, updatedAt`
Mirrors Module 3's output; Module 4 does not compute these values.

### certificates
`id, certificateId, internshipId, studentId, companyId, dataSnapshot{studentName, companyName, internshipTitle, startDate, endDate}, certificateHash, signature, verificationUrl, status, issuedAt, createdAt, updatedAt`
`dataSnapshot` fields originate from Module 1 (fetched at issue time);
`certificateHash`, `signature`, `certificateId`, `verificationUrl`, `status` are generated by Module 4.

### audit_logs
`id, actorId, action, entityType, entityId, metadata, timestamp`
`metadata` is intentionally minimal — booleans/status strings only, never message content.

## Notes
- Schema shown as Mongoose/MongoDB (matches the implementation). The same
  shapes map cleanly to relational tables if the team's shared database is
  SQL — replace ObjectId references with foreign keys and `participantIds[]`
  with a join table (`conversation_participants`).
- All cross-module references (`recipientId`, `studentId`, `companyId`,
  `internshipId`) are **unenforced foreign keys** — Module 4 trusts IDs
  supplied by Module 1's adapter/API rather than owning referential integrity
  for those entities.
